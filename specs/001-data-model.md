# 001 Data model and invariants

## Scope
PostgreSQL is the source of truth. All identifiers are UUIDs generated by the application; timestamps are UTC and come from an injectable clock. Monetary values are integer minor units with an ISO currency code.

## Tenant and catalog
- `organizers(id, name, api_key_hash, created_at)` isolates organizer-owned rows.
- `venues(id, organizer_id, name)`; `events(id, organizer_id, venue_id, name, starts_at, sale_opens_at, sale_closes_at, status, paused)`.
- `sections(id, event_id, name, mode)` where mode is `reserved` or `general_admission`.
- `seats(id, section_id, label, price_tier_id)` for reserved inventory.
- `price_tiers(id, event_id, currency, amount_minor)`.
- General admission inventory is represented by one row per section with `capacity`, `held`, and `sold`; reserved inventory uses one row per seat with `held_until`, `hold_id`, and `sold_order_id`.

Every tenant-scoped query includes `organizer_id` (or derives it through the event) and authorization is checked before returning data.

## Commerce
- `holds(id, event_id, buyer_id, expires_at, status, idempotency_key)` and `hold_items(hold_id, seat_id, quantity, unit_amount_minor)`.
- `orders(id, organizer_id, event_id, buyer_id, hold_id, currency, total_minor, state, version, created_at)`.
- `order_events(id, order_id, from_state, to_state, reason, created_at)` is append-only.
- `idempotency_keys(organizer_id, actor_id, key, request_hash, status_code, response_json, expires_at)` has a unique actor/key constraint.
- `charges(id, order_id, attempt, provider_id, amount_minor, currency, state)` has unique `(order_id, attempt)` and provider event IDs are unique.
- `tickets(id, order_id, seat_id, token_hash, token_payload, state)` has unique `(order_id, seat_id)` and one ticket set per order.

## Async and operations
- `outbox(id, topic, aggregate_id, payload, attempts, next_attempt_at, status, created_at)` is written in the same transaction as domain changes.
- `dead_letters(id, origin, payload, error_history, attempts, first_failed_at, last_failed_at, status, discard_reason)` stores exhausted outbox, webhook, and recovery work. Replays create a new idempotent outbox attempt and retain the original record.
- `webhook_events(provider_event_id, received_at, verified, payload, processed_at)` prevents replay and makes durable receipt precede the 2xx response.
- `scans(ticket_id, scanned_at, device_id)` has one successful-use record per ticket.

## Invariants
1. For every general-admission row: `sold >= 0`, `held >= 0`, and `sold + held <= capacity`; updates use a guarded SQL `UPDATE` in a transaction.
2. A reserved seat has at most one active hold and at most one sold order; hold expiry is changed only by the reaper or checkout transaction.
3. An order can have only one successful charge for an attempt and one ticket set; retries return persisted idempotent responses.
4. Every state transition has exactly one append-only order event and is performed through the state-machine service.
5. A successful scan inserts at most one use row under a unique constraint; concurrent scans return one success and one already-used response.
6. Every durable outbound effect has an outbox row; exhausted work has a DLQ row and cannot block later messages.
7. Refunds decrement sold inventory only once and are linked to a compensating charge/refund operation.
8. Expired holds are not chargeable and reaping cannot release inventory sold by a concurrent checkout.

## Transaction rules
Inventory claims use row locks or conditional updates and check affected-row count. Domain mutation, order event, and outbox event commit atomically. Consumers use unique natural keys and are safe to execute repeatedly. No correctness decision depends on Redis.
